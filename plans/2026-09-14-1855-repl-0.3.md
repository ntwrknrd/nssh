# REPL and multi-host commands for nssh 0.3

Status: proposed implementation plan; no runtime changes implemented.

## Direction

Add `nssh repl` as a normal command in the 0.3 series. Use the features and
operator experience from `origin/tui` as design evidence, then implement them
against current inventory, credentials, and SSH code. Keep a single Go binary
and the existing installation path. No activation flag, feature configuration,
separate beta installation, or 0.4 branch is needed.

The user requested planning, including documentation, rather than implementation.
The first delivery covers multi-host execution and a usable interactive REPL.
Output comparison and incremental output are follow-ups within this plan.

## User-visible behavior

### Entry points and compatibility

`nssh repl` opens the interactive interface when stdin and stdout are terminals.
It uses plain line input when either stream is redirected. `--plain` selects
that presentation explicitly; it does not enable the feature. `--concurrency N`
controls simultaneous host work. Start with a default of four and reject values
below one. Avoid adding global configuration for these choices.

Keep the current root parser and `nssh [ssh-options] HOST [command]` behavior.
Commas and brackets gain meaning only inside the REPL. The original invocation
with a quoted comma-separated hostname remains a single-host invocation.

Adding the command reserves the name `repl`. Connecting to a host with that name
uses `nssh --target repl`. Document and test this collision explicitly. Preserve
`user@repl`, SSH option precedence, remote command arguments, `--select`, literal
targets, SCP, and existing subcommands.

### Targets and commands

Use the historical grouped notation as the initial grammar. It separates targets
from remote command text without competing with root SSH syntax:

```text
[ 'irn-border-sw1', 'irn-border-sw2', 'irn-agg-sw1', 'irn-agg-sw2' ] ( 'show env power' )
[ 'irn-border-sw(1,2)', 'irn-agg-sw(1,2)' ] ( 'show env power', 'show version' )
[ 'select:provider:netbox group:network' ] ( 'show version' )
[ '2001:db8::10' ] ( 'show version' )
```

The selector example is illustrative; actual provider/group names come from the
user's inventory. Keep matching consistent with `nssh inv list`: case-insensitive
regular expressions for plain terms, exact `field:value` terms, and AND across
terms. Reuse its fields and field meanings.

- Accept single-quoted targets and commands, comma-separated inside their
  groups. Support `\'` within a quoted value; preserve other backslashes.
- Expand a trailing `prefix(1,2)` into explicit hosts. Do not add ranges, nested
  expansion, local shell expansion, or another expression language.
- Permit one selector by itself, or a list of explicit targets. Reject mixed
  selectors and targets with a useful message.
- Treat explicit targets as literal identities: exact managed names/aliases
  retain inventory policy; unmatched destinations use current literal-target
  behavior. Do not silently choose a partial match or create inventory entries.
- Support `user@host` through existing resolution. Deduplicate equivalent
  managed aliases with the same effective username; keep different usernames
  and separately configured inventory identities distinct.
- Resolve the full target set before executing any command. Keep explicit
  order; sort selector results consistently. Show resolved identities and the
  target count as execution starts, without an extra confirmation step.
- Pass each parsed command unchanged to the remote command mechanism. This is
  not a local shell, persistent remote shell, or interactive login session.

The same parser supports piped input. For example, in fish:

```fish
printf '%s\n' "[ 'irn-border-sw(1,2)' ] ( 'show env power' )" | nssh repl
```

Do not add a second one-shot command surface in the initial delivery. Piped input
covers shell use while the interactive grammar matures.

### Scheduling, failures, and cancellation

Allow one active submission per REPL. Execute commands in listed order for each
host, with at most N hosts active. A slow host does not block unrelated hosts
from advancing to their next command. This intentionally improves on the old
command-wide barrier.

A failed command stops subsequent commands for that host; other hosts continue.
Show later commands as skipped. Do not retry a remote command automatically.
Record queued, running, completed, failed, cancelled, and skipped states with
host, command, and exit/error details. Never label queued or cancelled work as
successfully completed.

Ctrl-C cancels the active submission, waits for local workers and request-owned
resources to finish cleanup, and returns to the prompt. A new submission cannot
start while old workers still own resources. Ctrl-C while idle exits; `:quit`,
`:exit`, and EOF also exit. Cancellation ends local SSH work but cannot promise
to undo commands already executed remotely or terminate every remote process.
Keep the existing connection timeout meaning; do not turn it into a command
deadline.

Interactive failures remain visible while the prompt stays usable; a normal quit
returns zero. Piped input processes submissions sequentially, stops after the
first failed submission, and returns one. Successful input returns zero;
interruption returns 130. Preserve original per-host exit codes and error types
in results. Piped input must never return success after a failure.

### Output and the interactive interface

Provide an editable prompt, in-context help, host completion, up/down history,
a scrollable transcript, per-host command headers, and live progress. Completion
works at the active target token in a multi-target line, even when command text
already exists. It never rewrites commands or collapses distinct hosts merely
because their short names match. Tab completes a unique match or common prefix
and shows remaining candidates; a multi-select picker can follow later.

Use the existing Go/Charm dependencies and a small UI model. Start with a stacked
result layout and keyboard scrolling. Keep terminal-native text selection
available; do not reproduce custom mouse selection, mouse escape filtering,
cursor themes, or clipboard integration.

In the first delivery, progress updates while commands run and full retained
output appears when each command finishes. Display completed results promptly,
even when an earlier target is slow. Give each result a stable host/command
identity; show the final summary in requested order. The UI must not claim
incremental output streaming.

Preserve stdout and stderr separately in the execution model. Interactive
presentation shows both with stream identity. Plain mode sends remote stdout to
stdout and remote stderr/status to stderr with host/command attribution. Buffer
presentation per completed command to prevent host output from interleaving.
Piped presentation adds no prompt, UI control sequences, or color. Preserve
remote stream bytes internally; do not claim a total ordering between OS streams.

Bound REPL capture and transcript retention. Proposed initial limits are 8 MiB
of retained stdout/stderr combined per command and 32 MiB for session output,
with finite metadata and event retention as well. Mark truncation/eviction
visibly while continuing to drain SSH output and record the command outcome.
Avoid duplicate full-output copies. Apply these limits only to the REPL;
preserve existing root command capture behavior. Limits should be implementation
constants initially, with focused tests rather than more configuration flags.

Persist interactive command history in the XDG state directory as `repl_history`,
with private file permissions and bounded storage. Retain at most 1,000 entries
and 1 MiB on disk, including safe handling of concurrent REPL instances. History
contains submitted command text, which may be sensitive; it does not contain
resolved credentials or remote output. Piped sessions do not write history.
Report history failures without preventing command execution.

### Follow-up features

- **Compare selected results:** side-by-side output with line differences and a
  stacked fallback on narrow terminals. Select two results explicitly; do not
  pair by adjacency or rerun commands. Bound comparison work and indicate
  truncated input. This can follow within 0.3.
- **Incremental output:** add request-scoped chunk delivery only after defining
  ordering, retention, backpressure, and cancellation behavior. Keep result
  identities and scheduling reusable so this does not require another backend.
- **Completion picker:** add multi-select interaction if basic target completion
  proves insufficient. It does not block the first delivery.

The JSON broker, Rust frontend, frontend plugin system, and general workflow
engine are outside this plan. The existing runtime agent retains its current
credential-provider responsibility.

## Implementation shape

| Owner | Responsibility |
| --- | --- |
| `internal/app` and `internal/cli/repl` | Register command; validate options; choose terminal/plain presentation; map final process status. |
| `internal/repl` | Parse submissions; expand targets; schedule host jobs; emit typed results; manage history. Keep terminal rendering outside the core. |
| `internal/connect` | Resolve current inventory and credentials; run commands through existing host-key, proxy, audit, and cleanup paths with explicit I/O. |
| `internal/ssh/captured` | Run OpenSSH, drain pipes, capture output and exit results, and honor cancellation. No REPL, UI, or inventory dependencies. |
| REPL presentation under `internal/repl` | Render prompt, progress, transcript, and plain output using shared UI conventions. |

Refactor the shared remote-command path to return structured results and accept
request-scoped I/O and interaction hooks. Keep existing root functions as wrappers
that preserve their presentation. Do not use a second authentication path or
swap process streams, environment variables, or global prompt functions around
concurrent requests. Package-level test hooks are not runtime injection points.

Build a catalog snapshot for each submission and use the same identities for
selection, execution, and attribution. Reuse `HostCatalog` and the selector
matcher; adapt selector rows to existing `inv list` semantics. Keep shared
selector code below CLI if the new core needs it. No automatic remote inventory
refresh, generated SSH config dependency, or credential caching in the REPL.

Every SSH-family subprocess in the command lifecycle must use request-scoped
I/O, including cold multiplexing startup. Today, `defaultMuxStartExec` in
`internal/ssh/connector/muxcheck_unix.go` inherits all three process streams.
In REPL mode, remote command workers and mux startup receive EOF as stdin and
route output/diagnostics to the correct host result; root wrappers keep existing
stdio behavior. Host-key probes and prompts use the same interaction owner.

Known-host verification and provider prompts need an explicit path: serialize
terminal interaction through one owner and suspend/resume UI input as necessary.
Use existing trust choices and request-scoped target/proxy askpass channels.
Noninteractive input reports a host failure when interaction is required instead
of reading submission text as a response. Cover key-only and password targets,
managed proxies, hot/cold multiplexing, and shared provider access. A semaphore
around command execution does not itself serialize provider prompts.

Use a fixed worker pool, finite queues, and per-submission context. Do not start
one goroutine per host/command combination or share mutable resolved secrets.
Retain existing audit semantics and record a terminal outcome for each started
command. Limit coordination around shared known-host writes, multiplexing setup,
and provider interactions to the resources that require it.

## Delivery steps and evidence

1. **Prepare shared execution.** Introduce explicit I/O, result, and interaction
   seams behind current root behavior. Verify existing argument precedence,
   stdout/stderr handling, stdin forwarding, capture drain, authentication,
   host-key, proxy, audit, and cleanup tests before adding REPL consumers.
   Include a cold-mux test proving startup cannot consume piped submissions or
   write diagnostics outside the attributed result path.
2. **Implement the core and plain command.** Add parser, catalog selection,
   worker scheduling, cancellation, and process-status handling. Test mixed
   successes/failures, duplicate aliases, distinct usernames, zero matches,
   quoting, IPv6, invalid input, EOF, large output, and noninteractive prompts.
   Include the user's four-switch example as a deterministic fixture.
3. **Add the interactive interface.** Implement prompt editing, target completion,
   bounded history, transcript, progress, and serialized interaction. Test input
   ownership, cancellation followed by another submission, resize, wrapping,
   long lines, copy/select behavior, and output arriving during a prompt.
4. **Complete documentation and validation.** Ship the normal command when the
   core and UI meet these checks. No hidden-command period or feature activation
   step is needed. Follow-up features can ship independently.

Use injected runners, fake credential providers, temporary configuration/state,
and local SSH fixtures for deterministic tests. Run focused tests and race tests
on changed concurrent packages, then `make test`, help snapshot validation, and
the existing macOS/Linux CI checks. Test terminal behavior on macOS and Linux
with an attached TTY and with pipes. Failures in host trust, key/password auth,
managed proxy use, interrupted work, or existing root syntax block delivery.
Production device access and installation are outside this planning task.

## Completion criteria for the first delivery

- The four-switch example uses current inventory and credential policy with
  attributed output, per-host outcomes, and bounded concurrency.
- Interactive and piped modes share parsing/execution; piped input cannot be
  consumed by an SSH worker or a trust prompt.
- Existing root SSH/SCP syntax and behavior remain covered; the reserved `repl`
  name and its literal-target escape are documented and tested.
- Cancellation returns the terminal to a usable state after local cleanup;
  queued work does not start later, and terminal outcomes remain truthful.
- History, output retention, terminal interaction, and shared resources have
  explicit limits and focused tests.
- Documentation, help snapshots, and repository checks describe and verify the
  implemented behavior. No extra runtime or activation configuration is needed.
