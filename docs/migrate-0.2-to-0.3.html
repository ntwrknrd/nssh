Release candidate beta guide

Migrate nssh 0.2 to 0.3

A rollback-safe migration from the 0.2 local vault and context model to 0.3 YAML inventory, external credential providers, and SSH-compatible automatic authentication.

Source: nssh 0.2.4 Target: nssh 0.3 RC macOS and Linux Updated 2026-08-06
This is a cutover, not an in-place config upgrade.

nssh 0.3 does not read config.toml, open the 0.2 credentials.age vault, or use 0.2 contexts as runtime inventory. Back up first. Do not run reset or a non-preserving uninstall during migration.

Start here

Migration at a glance

Preserve the complete 0.2 installation, install the matching 0.3 RC binaries, create new YAML configuration, import OpenSSH hosts, map authentication to an external provider, then test representative SSH and SCP paths before cleaning anything up.

Step 1

Preserve your 0.2 installation

Run these commands while the 0.2 binary and vault are still usable. The backup honors XDG overrides and preserves permissions. 

nssh --version
nssh lock

backup_dir="$HOME/nssh-0.2-backup-$(date +%Y%m%d-%H%M%S)"
nssh_config_home="${XDG_CONFIG_HOME:-$HOME/.config}"
nssh_data_home="${XDG_DATA_HOME:-$HOME/.local/share}"
nssh_state_home="${XDG_STATE_HOME:-$HOME/.local/state}"

mkdir -m 700 "$backup_dir"
copy_if_present() {
  if [ -e "$1" ]; then
    cp -a "$1" "$2"
  fi
}

copy_if_present "$nssh_config_home/nssh" "$backup_dir/config-nssh"
copy_if_present "$nssh_data_home/nssh" "$backup_dir/share-nssh"
copy_if_present "$nssh_state_home/nssh" "$backup_dir/state-nssh"
copy_if_present "$HOME/.ssh/config" "$backup_dir/ssh-config"
copy_if_present "$HOME/.ssh/conf.d" "$backup_dir/ssh-conf.d"

printf 'Backup: %s\n' "$backup_dir"
Check custom paths.

If 0.2 used custom recording, archive, SSH include, or XDG paths, copy those too. Keep the old binary and backup until every required credential has been tested in 0.3.

Capture the old model

nssh ctx list
nssh host list
nssh self cfg

Record context names and domains, host aliases, destination names, ports, usernames, SSH include files, and whether each representative host uses key or password authentication. Transfer passwords directly to the new provider; never paste them into notes, tickets, YAML, or shell history.

Step 2

Install the 0.3 release candidate

Use the RC download or installation instructions supplied with your beta invitation. Install nssh and nssh-askpass from the same build. Password-backed login fails when the helper is missing or mismatched. 

nssh --version

nssh_bin="$(command -v nssh)"
askpass_bin="$(dirname "$nssh_bin")/nssh-askpass"
printf 'nssh: %s\naskpass: %s\n' "$nssh_bin" "$askpass_bin"
test -x "$askpass_bin" && echo "askpass helper: ready"
The retained 0.2 TOML file is safe.

A preserved config.toml does not block 0.3 initialization because 0.3 looks for config.yaml.

Step 3

Create the 0.3 YAML configuration

Initialize once, then add the credential and inventory providers you need.

nssh self init

# Add providers explicitly if they were not selected during setup.
nssh self init --cred sops-age
nssh self init --inv local

nssh self cfg --paths
nssh self cfg --source

Provider includes live beneath ~/.config/nssh/credential/ and ~/.config/nssh/inventory/ by default. The root YAML activates them through includes.

Settings that do not translate directly
  • Remove 0.2 vault lockout, KDF, and agent.security settings.
  • Move default usernames into inventory auth policy.
  • Move recording dimensions to logging.export.gif.
  • Schedule nssh log archive externally; archive jitter and background scheduling do not migrate.
  • Put reusable OpenSSH options under ssh.defaults.options.
  • Keep agent settings only when retained 1Password or Bitwarden access is intentional.
Step 4

Convert contexts and import hosts

Create local groups for shared policy before importing SSH config. A 0.2 context domain generally becomes a 0.3 match.domain_suffix; context fallback auth becomes group auth policy. 

inventory:
  providers:
    local:
      type: local
      groups:
        work:
          match:
            domain_suffix:
              - .example.com
          auth:
            mode: password
            credential_provider: op-work
            username: netops
            password_ref: op://Work/network-admin/password
Apex domains need review.

In 0.2, example.com could match both the apex and its subdomains. In 0.3, .example.com matches subdomains, not the apex host itself. Assign the apex host explicitly when needed.

Import the OpenSSH tree

nssh self import ssh-config

Review the presented diff and every warning. The importer follows Include directives, writes global Host * options to the root config, and writes concrete hosts to local inventory. Existing inventory identities are skipped rather than overwritten.

  • Wildcard or negated host patterns and Match blocks are not inventory entries.
  • CanonicalizeHostname is not imported.
  • Unknown directives are retained only when accepted by the typed 0.3 schema.
  • An imported User without an inferred auth mode becomes password mode; correct key-auth hosts before testing.
Step 5

Recreate authentication mappings

nssh 0.3 has no local password vault. Put secrets in SOPS+age, 1Password, or Bitwarden, then store only provider names and references in inventory auth policy.

Shared credential

Prefer group auth when several hosts use the same account and provider item.

nssh inv set local/work \
  --auth password \
  --cred op-work:op://Work/network-admin/password \
  --user netops

Host exception

Use host auth for key-only hosts or exceptions to shared group policy.

nssh inv set edge01.example.com \
  --auth key \
  --user netops
Never migrate plaintext passwords through files or flags.

Add the secret directly to the external provider. Confirm the exact --cred syntax with nssh inv set --help; interactive selection is safer when a reference contains shell punctuation.

Step 6

Verify before cleanup

Run the bounded checks in order. Replace placeholders with non-sensitive test targets.

nssh self status
nssh self cfg --paths
nssh self cfg --source
nssh inv status
nssh inv list
nssh inv get <representative-host>

nssh -v <representative-key-host> true
nssh -v <representative-password-host> true
nssh agent status
Acceptance criterion

Migration is complete only when identity, username, destination, port, SSH options, auth provider/reference, proxy behavior, SSH, and SCP match the intended 0.2 behavior.

Step 7

Clean up only after acceptance

Existing recordings, archives, audit logs, and benchmark artifacts can remain in their XDG locations. External inventory provider JSON is a refreshable non-secret cache; do not hand-edit it.

Keep these 0.2 artifacts in the rollback backup until the RC is accepted:

  • config.toml, credentials.age, age.pub, age.key.enc, and piv.json
  • legacy backup files and nssh shell-integration scripts
  • old Fish, Zsh, or Bash completion files
  • nssh-managed files beneath ~/.ssh/conf.d/
Do not delete all of ~/.ssh/conf.d.

It may contain files owned by you or another tool. Remove only confirmed nssh-owned includes and shell startup lines. You may keep OpenSSH files intentionally for direct ssh compatibility.

Recovery

Rollback

Reinstall the saved 0.2 binary and restore the preserved 0.2 config, vault, SSH includes, and XDG state paths as one set. Do not point a 0.2 binary at 0.3 YAML or a 0.3 binary at the 0.2 credentials.age vault.

  1. Stop using the 0.3 RC.
  2. Restore the saved 0.2 binary and matching helper files.
  3. Restore config, data, state, and managed SSH files from the same backup.
  4. Verify nssh --version, contexts, hosts, and one representative connection.
  5. Keep the 0.3 YAML separate for diagnosis or a later retry.
