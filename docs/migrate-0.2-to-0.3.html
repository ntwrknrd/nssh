Migrate nssh 0.2 to 0.3

Moving your hosts and automatic logins to the 0.3 release candidate. Baseline 0.2.4, macOS and Linux. Updated 2026-08-06.

Keep your 0.2 files until you finish testing. 0.3 uses new settings and does not convert your 0.2 setup for you. Do not run nssh self reset or delete old files during the beta.

What changed

  • New config format. 0.3 writes YAML settings instead of the old TOML file.
  • Passwords move out of config. Pick SOPS+age, 1Password, or Bitwarden; nssh fetches the password when you connect.
  • Connecting is simpler. nssh HOST, the same way you would run ssh HOST.

Let an agent do it

If you use Codex or another agent with the nssh skill installed, this is the shortest path. Give it: 

Use the nssh skill to migrate my nssh 0.2 setup to 0.3. Back up my
existing setup first, explain any choices I need to make, never
display or copy my passwords, and test a host with me before cleanup.

The skill knows the current commands, file layout, and credential options. Otherwise, follow the four steps below.

1. Back up 0.2

Before installing the RC, copy your nssh and SSH files somewhere private:

backup="$HOME/nssh-0.2-backup-$(date +%Y%m%d-%H%M%S)"
mkdir -m 700 "$backup"
cp -a "$HOME/.config/nssh"       "$backup/config-nssh" 2>/dev/null || true
cp -a "$HOME/.local/share/nssh"  "$backup/share-nssh"  2>/dev/null || true
cp -a "$HOME/.local/state/nssh"  "$backup/state-nssh"  2>/dev/null || true
cp -a "$HOME/.ssh/config"        "$backup/ssh-config"  2>/dev/null || true
cp -a "$HOME/.ssh/conf.d"        "$backup/ssh-conf.d"  2>/dev/null || true

Keep the folder private; it can contain encrypted credentials and host names. If you moved nssh's storage locations, confirm the backup with your beta coordinator first.

2. Install and initialize 0.3

Install the RC build from your beta invitation, then run the guided setup:

nssh --version
nssh self init

Which credential provider? Whichever password manager you already use. If you use neither 1Password nor Bitwarden, choose SOPS+age. Never put a plaintext password in an nssh YAML file.

3. Import your hosts

Pull in the hosts you already have in your SSH config:

nssh self import ssh-config

Review the preview and accept it if the host names and usernames look right. Then point each host or group at the credential provider you chose: 

nssh inv list
nssh inv set myhost --user admin --auth password --cred onepassword
nssh inv set local/switches --cred sops

Run nssh inv set --help for the full flag list. If your 0.2 setup shared one password across many hosts, set it on the group rather than on each host — this is where the nssh skill saves the most time.

4. Test your usual logins

Start with one familiar host. It should log in with no password on the command line:

nssh YOUR-HOST

Then confirm each case you actually rely on:

  • A normal host connects.
  • A password host pulls the right credential automatically.
  • A host behind a jump host connects.
  • nssh cp copies a test file.

Keep the 0.2 backup for the whole beta, even after everything passes.

If something breaks

Do not reset nssh or delete files. Ask your beta coordinator, or hand an agent with the nssh skill this: 

Use the nssh skill to troubleshoot my 0.2 to 0.3 migration. Inspect my
setup without showing secrets or connecting to a host until I approve
it. Preserve my 0.2 backup.

To go back to 0.2 immediately: reinstall the 0.2 release and restore the nssh and SSH folders from your backup. Leave the 0.3 files in place so they can still be inspected.

Report an issue

File it at github.com/ntwrknrd/nssh/issues. Never attach passwords, tokens, internal host names, or a full config dump.
